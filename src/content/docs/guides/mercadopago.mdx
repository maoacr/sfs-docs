SFS usa **MercadoPago Checkout Pro** para procesar pagos de reservas. Cada pago crea una *preference* y el jugador paga en el checkout de MP.

:::note[Split de pagos: pendiente]
El reparto 85% dueño / 15% plataforma **todavía no está implementado**. Hoy el 100% del pago llega a la cuenta de MP de la plataforma. El split requiere que cada dueño vincule su cuenta de MP (OAuth de marketplace) y queda para una fase posterior.
:::

## Requisitos

1. Cuenta de desarrollador en [MercadoPago Developers](https://www.mercadopago.com.co/developers/panel)
2. Una aplicación creada en el panel
3. Credenciales de prueba (sandbox) y/o producción

## Variables de entorno

```bash
# .env
MP_ACCESS_TOKEN="TEST-xxx"      # Access token de la aplicación
MP_PUBLIC_KEY="TEST-xxx"        # Public key de la aplicación
MP_WEBHOOK_SECRET="xxx,yyy"     # Claves de webhooks — las genera MP. Varias, separadas por coma
APP_URL="https://..."           # URL pública: MP la usa para back_urls y notificaciones
```

| Variable | Descripción |
|---|---|
| `MP_ACCESS_TOKEN` | Token de acceso del servidor. Con prefijo `TEST-` el checkout usa `sandbox_init_point`; con `APP_USR-`, `init_point` |
| `MP_PUBLIC_KEY` | Llave pública para el frontend. Mismo prefijo que el access token |
| `MP_WEBHOOK_SECRET` | **Claves secretas que genera MercadoPago** en Tu aplicación → Webhooks. Admite **varias separadas por coma**: vale la firma que coincida con cualquiera. Si ponés un valor inventado, ninguna firma coincide y todas las notificaciones responden 401 |
| `APP_URL` | Base de `notification_url` y `back_urls`. MP no puede notificar a `localhost` |

:::caution[`back_urls` sin `auto_return` no redirige]
Definir las `back_urls` no alcanza: MP sólo las dispara si la preference manda `auto_return: "approved"`. Sin eso el jugador se queda en el comprobante de MP, con un botón "Volver al sitio" que muchos no tocan — el pago entra igual por el webhook, pero la persona cree que falló.
:::

## Sandbox (desarrollo)

### 1. Obtener credenciales de prueba

Panel MP → Tu aplicación → **Credenciales de prueba**:
- **Public Key**: `TEST-xxxxxxxx-xxxx-...`
- **Access Token**: `TEST-xxxxxxxxxxxx-...`

### 2. Crear usuarios de prueba

Panel MP → Tu aplicación → **Cuentas de prueba**. Necesitás crear **dos** usuarios:

| Rol | Para qué |
|---|---|
| **Vendedor (Seller)** | Genera las credenciales. El User ID del seller debe coincidir con el sufijo del Access Token |
| **Comprador (Buyer)** | Es el que usás para pagar en el checkout de MP |

El panel muestra la contraseña al crear el usuario y después ya no. Si la perdiste, creá otro comprador por API — la respuesta la trae:

```bash
curl -s -X POST https://api.mercadopago.com/users/test \
  -H "Authorization: Bearer $MP_ACCESS_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"site_id":"MCO","description":"comprador de prueba"}' | jq
```

`MCO` es Colombia, y coincide con el `currency_id: "COP"` de la preference. Devuelve `id`, `nickname`, `email` y `password`.

### 3. Tarjetas de prueba

Usá estas tarjetas en el checkout de MP (después de loguearte con el buyer):

| Tarjeta | Número | CVV | Vencimiento | Resultado |
|---|---|---|---|---|
| Mastercard | `5254 1336 7440 3564` | `123` | `11/30` | ✅ Aprobada |
| Visa | `4013 5406 8274 6260` | `123` | `11/30` | ✅ Aprobada |
| Visa Débito | `4915 1120 5524 6507` | `123` | `11/30` | ✅ Aprobada |

### 4. Recibir webhooks

MP no puede llamar a `localhost`. Hay dos caminos:

- **Contra el deployment** (recomendado): ya existe una URL pública de producción. Apuntá el webhook del panel ahí y probá con credenciales `TEST-`. No hace falta túnel.
- **Contra tu máquina**: exponé el dev server con un túnel (`cloudflared`, `ngrok`) y usá esa URL pública como `APP_URL` y como URL del webhook.

Ver [Despliegue](/guides/despliegue) para la URL y la verificación de que el endpoint es alcanzable.

### 5. Probar el flujo

1. Levantá el dev server (`pnpm dev`) y el túnel
2. Creá una reserva como player
3. Al pagar, te redirige al checkout de MercadoPago
4. **Importante**: si tenés sesión de MP abierta, **cerrala primero** (o usá una ventana de incógnito)
5. Logueate con el **buyer test user** (email y contraseña del panel)
6. Pagá con una tarjeta de prueba
7. MP te redirige de vuelta y el webhook confirma el pago

:::caution
Si intentás pagar con tu cuenta real de MP en modo sandbox, MP rechaza la transacción porque no sos un test user. Siempre usá el buyer test user.
:::

## Webhook

### Configuración

En el panel de MP → Tu aplicación → **Webhooks**. Hay **dos pestañas**, `Modo de prueba` y `Modo productivo`, y son configuraciones independientes: cada una con su URL y **su propia clave secreta**.

| Campo | Valor |
|---|---|
| URL | `https://tu-dominio.com/api/webhooks/mercadopago` (la misma en las dos pestañas) |
| Eventos | **`Pagos (legacy)`** |
| Clave secreta | La genera MP — copiá **las dos**, separadas por coma, a `MP_WEBHOOK_SECRET` |

:::caution[Marcá `Pagos (legacy)`, no `Order`]
El handler filtra con `if (tipo !== "payment")`. `Pagos (legacy)` es el topic que manda `type: "payment"`; `Order (Mercado Pago)` es la API nueva de Orders y manda otro type, así que el webhook lo descarta con un `200 OK`. Verde en el panel de MP, cero pagos aplicados.

La etiqueta "legacy" invita a esquivarlo y es justo el que hace falta.
:::

:::danger[El botón de refresh no muestra la clave: la regenera]
Tocarlo invalida la clave que ya tenés guardada en Vercel y te deja todo en `401`. Un clic de curiosidad cuesta un redeploy.
:::

### Por qué dos claves en una sola variable

MP firma cada notificación con la clave **del modo que originó el pago**, y el endpoint es uno solo. El problema es saber qué modo es:

- Pagando con **vendedor de prueba**, las notificaciones llegan como **modo productivo** — aunque estés probando. Sus credenciales arrancan con `APP_USR-` igual que las de una cuenta real.
- La doc de MP sugiere que los pagos de prueba van al modo de prueba. En la práctica no siempre.

Con una sola clave guardada, acertar el modo es una apuesta, y perderla se ve como `401` en todos los reintentos con el log del handler vacío — idéntico a una firma mal implementada. Por eso `verifyWebhookRequest` acepta una lista: guardás las dos y valida venga del modo que venga.

:::note[`APP_USR-` no significa plata real]
Un vendedor de prueba tiene su propia aplicación y sus credenciales productivas también arrancan con `APP_USR-`. Desde la variable de entorno es indistinguible de una cuenta real. Para saber de quién es el token:

```bash
curl -s -H "Authorization: Bearer $MP_ACCESS_TOKEN" \
  https://api.mercadopago.com/users/me | jq '{id, nickname, email}'
```

`nickname` tipo `TESTUSER…` → vendedor de prueba. Tu nickname real → el checkout cobra de verdad.
:::

`/api/webhooks/` es una ruta pública en `src/proxy.ts`: MP llama sin cookie de sesión, así que la autenticación es la firma. Si la ruta no fuera pública, el proxy redirigiría a `/auth/login` y el handler nunca se ejecutaría.

:::caution[El proxy no es la única capa que puede comerse el webhook]
Que MP "no llegue" ya pasó tres veces, cada vez en una capa distinta y **siempre en silencio**:

1. `src/proxy.ts` redirigía `/api/webhooks/` a `/auth/login`
2. **Vercel Authentication** devolvía `401` antes de ejecutar el handler
3. El **WAF de Cloudflare** desafía POSTs de servidores — MP no resuelve challenges de JS

El síntoma es idéntico en los tres casos: MP reintenta, el log del handler queda vacío, y parece un problema de firma. Antes de revisar la firma, comprobá **quién contesta**:

```bash
curl -s -X POST -H 'Content-Type: application/json' -d '{"type":"ping"}' \
  https://tu-dominio/api/webhooks/mercadopago
# JSON de la app → la request llegó
# HTML de login  → una capa de adelante la frenó
```
:::

### Verificación de firma

Cada webhook incluye los headers `x-signature` (`ts=...,v1=...`) y `x-request-id`. El sistema:

1. Extrae `ts` y `v1` de `x-signature`
2. Construye el manifest: `id:{data.id};request-id:{x-request-id};ts:{ts};`
   - `data.id` se toma del query param y va en minúsculas si es alfanumérico
   - Las partes que MP no envía se omiten
3. Calcula HMAC-SHA256 del manifest con cada clave de `MP_WEBHOOK_SECRET`
4. Compara con `v1` usando `crypto.timingSafeEqual`; alcanza con que **una** coincida

Si no hay `MP_WEBHOOK_SECRET` configurado —o la lista queda vacía tras descartar entradas en blanco—, los webhooks se aceptan sin verificar (solo para desarrollo local).

### Doble verificación e idempotencia

- El webhook **consulta el pago a la API de MP** antes de tocar la base de datos, así que un webhook falsificado no puede aprobar nada.
- `external_reference` de cada preference es el **id del `Pago`**, así el webhook encuentra el registro exacto.
- MP envía varias notificaciones por pago (`created`, `updated`) y reintenta ante errores. El procesamiento corre en una transacción con `SELECT … FOR UPDATE` y un pago ya `APROBADO` nunca se vuelve a sumar a la reserva.
- Ante un error inesperado el webhook responde `500` para que MP reintente; los reintentos son seguros.

## Flujo de pago completo

```
1. Player crea reserva
   └── estado: PENDIENTE_PAGO, TTL: 15 min

2. Player inicia pago (POST /api/reservas/:id/pagar)
   └── Se registra un Pago PENDIENTE
   └── Se crea la preference en MP (external_reference = pago.id)
   └── Retorna checkoutUrl

3. Player paga en checkout de MP
   └── `auto_return: "approved"` lo devuelve solo a `back_urls.success`

4. MP envía webhook a /api/webhooks/mercadopago
   └── Verifica firma + consulta el pago a la API de MP
   └── Pago → APROBADO (una sola vez)

5. Sistema actualiza la reserva:
   ├── Si pagó 100% → CONFIRMADA
   ├── Si pagó ≥50% → PAGO_PARCIAL (saldo pendiente)
   └── Notifica a player y dueño (in-app + email)

6. Si PAGO_PARCIAL, el saldo se cobra por:
   ├── POST /api/reservas/:id/pagar-saldo (player o compañero de partido)
   └── POST /api/reservas/:id/confirmar-pago (el dueño recibe efectivo/Nequi/transferencia)
```

## Cancelación, expiración y reembolso

Tanto `PATCH /api/reservas/:id/cancelar` como `PUT /api/reservas/:id` con `estado: CANCELADA` aplican la misma política (`src/lib/cancelacion.ts`):

| Escenario | Reembolso |
|---|---|
| Jugador cancela antes del plazo del complejo | 100% |
| Jugador cancela dentro del plazo | 100% − penalización |
| Dueño cancela | Siempre 100% |

**Expiración (TTL)**: solo expiran las reservas `PENDIENTE_PAGO` sin pago a los 15 minutos. Las `PAGO_PARCIAL` no expiran: ya pagaron el mínimo. Si MP aprueba un pago **después** de que la reserva expiró, el webhook lo reembolsa automáticamente.

El reembolso se procesa vía la API de MercadoPago (`PaymentRefund`).

## Producción

Para pasar a producción:

1. Cambiá las credenciales a las de **producción** (prefijo `APP_USR-`)
2. Configurá la URL del webhook con tu dominio real y copiá la clave secreta que genera MP
3. Asegurate de que `APP_URL` apunte al dominio de producción
4. Los test users y tarjetas de prueba **no funcionan en producción**

:::note[`APP_URL` exige redeploy, aunque no se hornee en el build]
Se lee del lado del servidor, así que **no** lleva el prefijo `NEXT_PUBLIC_` y no queda inlineada en el bundle del browser. Pero las variables de Vercel aplican a **deployments nuevos**: cambiar el valor no afecta al que está corriendo. Hay que redeployar.

Y las preferencias de pago ya creadas conservan las `back_urls` viejas: ver [migrar a un dominio propio](/guides/despliegue#migrar-a-un-dominio-propio).
:::

### La vuelta del checkout y las cookies

MP devuelve al jugador con un redirect a `back_urls` — una navegación que **nace en `mercadopago.com`**. Las cookies de sesión están en `SameSite=lax` precisamente por eso: con `strict` el browser no las adjunta, el proxy no ve sesión, y el jugador cae en `/auth/login` justo después de pagar.

Si alguna vez ves ese síntoma —"pagué y me deslogueó"— mirá el atributo `SameSite` antes que el flujo de pago. Detalle en [Seguridad](/guides/security#por-qué-lax-y-no-strict).

## Archivos clave

| Archivo | Qué hace |
|---|---|
| `src/lib/mercadopago.ts` | Wrapper del SDK — preferences, refunds, verificación de firma |
| `src/lib/pagos.ts` | Iniciar un pago y aplicar notificaciones de MP (idempotente) |
| `src/lib/cancelacion.ts` | Política de cancelación y reembolsos |
| `src/app/api/webhooks/mercadopago/route.ts` | Endpoint que recibe los webhooks de MP |
| `src/app/api/reservas/[id]/pagar/route.ts` | Inicia pago de reserva |
| `src/app/api/reservas/[id]/pagar-saldo/route.ts` | Paga saldo pendiente |
| `src/app/api/reservas/[id]/cancelar/route.ts` | Cancela reserva + reembolso |
