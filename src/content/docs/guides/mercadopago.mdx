SFS usa **MercadoPago Checkout Pro** para procesar pagos de reservas. Cada pago crea una *preference* y el jugador paga en el checkout de MP.

:::note[Split de pagos: pendiente]
El reparto 85% dueño / 15% plataforma **todavía no está implementado**. Hoy el 100% del pago llega a la cuenta de MP de la plataforma. El split requiere que cada dueño vincule su cuenta de MP (OAuth de marketplace) y queda para una fase posterior.
:::

## Requisitos

1. Cuenta de desarrollador en [MercadoPago Developers](https://www.mercadopago.com.co/developers/panel)
2. Una aplicación creada en el panel
3. Credenciales de prueba (sandbox) y/o producción

## Variables de entorno

```bash
# .env
MP_ACCESS_TOKEN="TEST-xxx"      # Access token de la aplicación
MP_PUBLIC_KEY="TEST-xxx"        # Public key de la aplicación
MP_WEBHOOK_SECRET="xxx"         # Clave secreta de webhooks — la genera MP, no vos
NEXT_PUBLIC_APP_URL="https://..." # URL pública: MP la usa para back_urls y notificaciones
```

| Variable | Descripción |
|---|---|
| `MP_ACCESS_TOKEN` | Token de acceso del servidor. Con prefijo `TEST-` el checkout usa `sandbox_init_point`; con `APP_USR-`, `init_point` |
| `MP_PUBLIC_KEY` | Llave pública para el frontend. Mismo prefijo que el access token |
| `MP_WEBHOOK_SECRET` | **Clave secreta que genera MercadoPago** en Tu aplicación → Webhooks. Si ponés un valor inventado, ninguna firma coincide y todas las notificaciones responden 401 |
| `NEXT_PUBLIC_APP_URL` | Base de `notification_url` y `back_urls`. MP no puede notificar a `localhost` |

## Sandbox (desarrollo)

### 1. Obtener credenciales de prueba

Panel MP → Tu aplicación → **Credenciales de prueba**:
- **Public Key**: `TEST-xxxxxxxx-xxxx-...`
- **Access Token**: `TEST-xxxxxxxxxxxx-...`

### 2. Crear usuarios de prueba

Panel MP → Tu aplicación → **Cuentas de prueba**. Necesitás crear **dos** usuarios:

| Rol | Para qué |
|---|---|
| **Vendedor (Seller)** | Genera las credenciales. El User ID del seller debe coincidir con el sufijo del Access Token |
| **Comprador (Buyer)** | Es el que usás para pagar en el checkout de MP |

### 3. Tarjetas de prueba

Usá estas tarjetas en el checkout de MP (después de loguearte con el buyer):

| Tarjeta | Número | CVV | Vencimiento | Resultado |
|---|---|---|---|---|
| Mastercard | `5254 1336 7440 3564` | `123` | `11/30` | ✅ Aprobada |
| Visa | `4013 5406 8274 6260` | `123` | `11/30` | ✅ Aprobada |
| Visa Débito | `4915 1120 5524 6507` | `123` | `11/30` | ✅ Aprobada |

### 4. Recibir webhooks en local

MP no puede llamar a `localhost`. Para probar el flujo completo en tu máquina, exponé el dev server con un túnel (por ejemplo `cloudflared` o `ngrok`) y usá esa URL pública como `NEXT_PUBLIC_APP_URL` y como URL del webhook en el panel.

### 5. Probar el flujo

1. Levantá el dev server (`pnpm dev`) y el túnel
2. Creá una reserva como player
3. Al pagar, te redirige al checkout de MercadoPago
4. **Importante**: si tenés sesión de MP abierta, **cerrala primero** (o usá una ventana de incógnito)
5. Logueate con el **buyer test user** (email y contraseña del panel)
6. Pagá con una tarjeta de prueba
7. MP te redirige de vuelta y el webhook confirma el pago

:::caution
Si intentás pagar con tu cuenta real de MP en modo sandbox, MP rechaza la transacción porque no sos un test user. Siempre usá el buyer test user.
:::

## Webhook

### Configuración

En el panel de MP → Tu aplicación → **Webhooks**:

| Campo | Valor |
|---|---|
| URL | `https://tu-dominio.com/api/webhooks/mercadopago` |
| Eventos | **Pagos** (`payment`) |
| Clave secreta | La genera MP — copiala a `MP_WEBHOOK_SECRET` |

`/api/webhooks/` es una ruta pública en `src/proxy.ts`: MP llama sin cookie de sesión, así que la autenticación es la firma. Si la ruta no fuera pública, el proxy redirigiría a `/auth/login` y el handler nunca se ejecutaría.

### Verificación de firma

Cada webhook incluye los headers `x-signature` (`ts=...,v1=...`) y `x-request-id`. El sistema:

1. Extrae `ts` y `v1` de `x-signature`
2. Construye el manifest: `id:{data.id};request-id:{x-request-id};ts:{ts};`
   - `data.id` se toma del query param y va en minúsculas si es alfanumérico
   - Las partes que MP no envía se omiten
3. Calcula HMAC-SHA256 del manifest con `MP_WEBHOOK_SECRET`
4. Compara con `v1` usando `crypto.timingSafeEqual`

Si no hay `MP_WEBHOOK_SECRET` configurado, los webhooks se aceptan sin verificar (solo para desarrollo local).

### Doble verificación e idempotencia

- El webhook **consulta el pago a la API de MP** antes de tocar la base de datos, así que un webhook falsificado no puede aprobar nada.
- `external_reference` de cada preference es el **id del `Pago`**, así el webhook encuentra el registro exacto.
- MP envía varias notificaciones por pago (`created`, `updated`) y reintenta ante errores. El procesamiento corre en una transacción con `SELECT … FOR UPDATE` y un pago ya `APROBADO` nunca se vuelve a sumar a la reserva.
- Ante un error inesperado el webhook responde `500` para que MP reintente; los reintentos son seguros.

## Flujo de pago completo

```
1. Player crea reserva
   └── estado: PENDIENTE_PAGO, TTL: 15 min

2. Player inicia pago (POST /api/reservas/:id/pagar)
   └── Se registra un Pago PENDIENTE
   └── Se crea la preference en MP (external_reference = pago.id)
   └── Retorna checkoutUrl

3. Player paga en checkout de MP

4. MP envía webhook a /api/webhooks/mercadopago
   └── Verifica firma + consulta el pago a la API de MP
   └── Pago → APROBADO (una sola vez)

5. Sistema actualiza la reserva:
   ├── Si pagó 100% → CONFIRMADA
   ├── Si pagó ≥50% → PAGO_PARCIAL (saldo pendiente)
   └── Notifica a player y dueño (in-app + email)

6. Si PAGO_PARCIAL, el saldo se cobra por:
   ├── POST /api/reservas/:id/pagar-saldo (player o compañero de partido)
   └── POST /api/reservas/:id/confirmar-pago (el dueño recibe efectivo/Nequi/transferencia)
```

## Cancelación, expiración y reembolso

Tanto `PATCH /api/reservas/:id/cancelar` como `PUT /api/reservas/:id` con `estado: CANCELADA` aplican la misma política (`src/lib/cancelacion.ts`):

| Escenario | Reembolso |
|---|---|
| Jugador cancela antes del plazo del complejo | 100% |
| Jugador cancela dentro del plazo | 100% − penalización |
| Dueño cancela | Siempre 100% |

**Expiración (TTL)**: solo expiran las reservas `PENDIENTE_PAGO` sin pago a los 15 minutos. Las `PAGO_PARCIAL` no expiran: ya pagaron el mínimo. Si MP aprueba un pago **después** de que la reserva expiró, el webhook lo reembolsa automáticamente.

El reembolso se procesa vía la API de MercadoPago (`PaymentRefund`).

## Producción

Para pasar a producción:

1. Cambiá las credenciales a las de **producción** (prefijo `APP_USR-`)
2. Configurá la URL del webhook con tu dominio real y copiá la clave secreta que genera MP
3. Asegurate de que `NEXT_PUBLIC_APP_URL` apunte al dominio de producción
4. Los test users y tarjetas de prueba **no funcionan en producción**

## Archivos clave

| Archivo | Qué hace |
|---|---|
| `src/lib/mercadopago.ts` | Wrapper del SDK — preferences, refunds, verificación de firma |
| `src/lib/pagos.ts` | Iniciar un pago y aplicar notificaciones de MP (idempotente) |
| `src/lib/cancelacion.ts` | Política de cancelación y reembolsos |
| `src/app/api/webhooks/mercadopago/route.ts` | Endpoint que recibe los webhooks de MP |
| `src/app/api/reservas/[id]/pagar/route.ts` | Inicia pago de reserva |
| `src/app/api/reservas/[id]/pagar-saldo/route.ts` | Paga saldo pendiente |
| `src/app/api/reservas/[id]/cancelar/route.ts` | Cancela reserva + reembolso |
