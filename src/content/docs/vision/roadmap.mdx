El desarrollo de SFS sigue un orden estricto de fases. Cada fase es prerrequisito de la siguiente.

## Fase 0: Blindaje del Backend

**Estado**: 🟢 Completada — 2026-08-09

Establece los cimientos de seguridad, validación y testing. Sin esto, todo lo demás es frágil.

| Tarea | Descripción | Prioridad | Estado |
|---|---|---|---|
| **0.1** | Zod en todas las API routes — validación de inputs en runtime | P0 | ✅ |
| **0.2** | Rate limiting — protección contra abuso y brute force | P0 | ✅ |
| **0.3** | Tenant isolation — filtro por `tenantId` (explícito por query desde la migración a Drizzle) | P0 | ✅ |
| **0.4** | CSRF protection — double-submit cookie + SameSite=strict | P0 | ✅ |
| **0.5** | Test suite inicial — Vitest + 14 tests de schemas | P0 | ✅ |

**Verificación**:
- `pnpm test` → 14/14 pasan (1.9s)
- `pnpm tsc --noEmit` → 0 errores
- Rate limiting responde 429 al exceder límite
- Toda query multi-tenant filtra por `tenantId`
- CSRF requerido para POST/PUT/PATCH/DELETE (excepto login/register)

**Stack agregado**: zod, vitest, @testing-library/react, nanoid

**Archivos clave**: `src/lib/schemas.ts`, `src/lib/api-handler.ts`, `src/lib/csrf.ts`, `src/lib/rate-limit.ts`

**Docs**: [Guía de Seguridad](/guides/security)

## Fase 1: El Corazón del Negocio

**Estado**: 🟢 Completada — 2026-08-10

Implementa la lógica de pricing, pagos con MercadoPago Checkout Pro, TTL real, políticas de cancelación y emails transaccionales. Incluye modelo de Partidos y Equipos para pagos compartidos.

| Tarea | Descripción | Prioridad | Estado |
|---|---|---|---|
| **1.1** | Motor de precios dinámicos — `tarifas` + `promociones` → precio final | P0 | ✅ |
| **1.2** | MercadoPago Checkout Pro + Webhooks con firma HMAC | P0 | ✅ |
| **1.2b** | Split Payments 85/15 — requiere OAuth de marketplace con las cuentas de los dueños | P1 | 🔴 |
| **1.3** | TTL de reservas — limpieza oportunista + Vercel Cron cada 5 min | P0 | ✅ |
| **1.4** | Políticas de cancelación y reembolso configurables por complejo | P0 | ✅ |
| **1.5** | Emails transaccionales — Resend con templates HTML | P0 | ✅ |
| **1.6** | Modelo de Partidos — pagos compartidos entre jugadores | P1 | ✅ |
| **1.7** | Modelo de Equipos — CRUD, invitar miembros, asignar a partidos | P1 | ✅ |
| **1.8** | Calendario público de partidos (seed para tournaments) | P2 | ✅ |

**Verificación**:
- `pnpm test` → 33/33 pasan
- `pnpm tsc --noEmit` → 0 errores
- Motor de precios con match de tarifa específica + promociones
- Pago con Checkout Pro; webhook idempotente (ver estabilización abajo)
- Pago mínimo 50%, bloqueo por saldo pendiente
- Cancelación con políticas configurables por complejo + refund MP
- Emails para PAGO_PARCIAL, RECIBO_PAGO, y notificaciones al dueño

**Stack agregado**: mercadopago, Vercel Cron

**Archivos clave**: `src/lib/pricing.ts`, `src/lib/mercadopago.ts`, `src/app/api/webhooks/mercadopago/`, `src/app/api/reservas/[id]/pagar/`, `src/app/player/reservar/[id]/`, `vercel.json`

## Estabilización: Migración a Drizzle + flujo de pagos

**Estado**: 🟡 En rama `feat/drizzle-migration` — 2026-09-24

La Fase 1 quedó marcada como completa, pero el flujo de pago real no funcionaba. Esta estabilización cierra la migración de Prisma a Drizzle y corrige las causas raíz.

| Tarea | Descripción | Estado |
|---|---|---|
| **E.1** | Migrar todas las rutas a Drizzle y eliminar Prisma (el alias `prisma = db as any` ocultaba fallos en runtime) | ✅ |
| **E.2** | Adaptadores DB ↔ API (`src/lib/db-mappers.ts`) para no romper el frontend | ✅ |
| **E.3** | Migración `0001`: dirección estructurada y `codigo_pais` | ✅ |
| **E.4** | Webhook y cron públicos en el proxy (antes redirigían a `/auth/login`) | ✅ |
| **E.5** | Firma del webhook con `request-id`; idempotencia con transacción y `FOR UPDATE` | ✅ |
| **E.6** | TTL solo expira `PENDIENTE_PAGO`; reembolso de pagos aprobados tras expirar | ✅ |
| **E.7** | Cancelación unificada con política de reembolso (`src/lib/cancelacion.ts`) | ✅ |
| **E.8** | Probar pago real en sandbox con buyer test user y túnel público | 🔴 |
| **E.9** | Merge a `main` y deploy | 🔴 |

**Verificación**:
- `pnpm test` → 55/55 pasan
- `tsc --noEmit` → 0 errores
- Webhook con dos notificaciones concurrentes del mismo pago → se aplica una sola vez

## Fase 2: Blindaje Legal y Seguridad Avanzada

**Estado**: 🔴 Pendiente (depende de Fase 1)

Cumplimiento de normativa colombiana (Ley 1581, facturación electrónica DIAN), security headers, logging y auditoría.

| Tarea | Descripción | Prioridad |
|---|---|---|
| **2.1** | Política de tratamiento de datos personales + consentimiento explícito | P0 |
| **2.2** | Términos y Condiciones con disclaimer de presencialidad | P0 |
| **2.3** | Estrategia de facturación electrónica | P0 |
| **2.4** | Security headers — CSP, HSTS, X-Frame-Options | P1 |
| **2.5** | Logging y auditoría de acciones críticas | P1 |

**Goals de la fase**:
- Registro de usuario incluye política de datos y consentimiento explícito
- Headers de seguridad presentes en todas las responses
- Log de todas las acciones críticas (reservas, pagos, cambios de precio)
- Estrategia de facturación definida y documentada

## Principios

- **Nunca asumir, siempre preguntar** — cada decisión de tradeoff se consulta
- **Verificar sobre asumir** — claims técnicos se validan con evidencia
- **Fase completada = fase verificada** — cada fase tiene criterios de aceptación
- **Documentación viva** — este roadmap se actualiza al completar cada tarea
